# V1.2.0 — 算过的东西不再算第二遍

`versionCode = 14` · 可从 1.1.8 直接覆盖安装

这一版没有新功能。四件事都指向同一个毛病：**应用在重算它已经算过的东西**。

## 增量扫描

扫描慢的不是遍历目录树，而是逐个文件打开读标签和时长。SAF 的列表查询本来就给出
`lastModified` 和 `length`，于是把这两个数做成指纹，与上一轮的缓存比对，没变就直接
复用旧条目。

判定用的是**与**：

- 两个数都得匹配。同一秒内原地重写只改长度，只信时间戳会把旧时长留在库里。
- 两个数都得有。provider 报 `0` 是「没有这个信息」，不是「没变化」。

文件夹管理页在扫完后会显示 `共 128 首 · 用时 1.2 s · 跳过 121 首未改动`——没有这行
汇总，「跳过」只是一个看不见的内部优化。

## 搜索

搜索框每次按键都会对全库每首曲目的名称、歌手、专辑各做一次小写化。三千首的库、
每个字符三万个字符串分配，重算的是两次按键之间根本没变的文本。

现在小写化和排序在曲目列表变化时做一次。索引挂在**它被构造时的两个值**上缓存，
所以「索引过期」不是不太可能，而是不可能——缓存键就是它的全部输入。

## 封面

内嵌封面常见 1000×1000，解码成位图是 4 MB。四十行列表为了填 52 dp 的方块会 churn
掉 160 MB。现在按显示尺寸分三档请求（160 / 320 / 1080 px），并且向上取整——向下
取整会让 Coil 把解码好的位图再放大回去，看起来是糊的。

零尺寸不会传给 Coil：那里的 `size(0)` 表示「不定尺寸」，正好是这套策略要消除的事。

## 播放队列

头部从「12 首」变成 `3/12 · 剩 34 分`，而且这个数在一首歌里平滑下降，不是按整首跳。
它不并排显示「剩 N 首」和时长——首数不含当前曲、时长含当前曲剩余，并排会读出
「剩 1 首 · 5 分」这种矛盾。

队列行可以长按拖动排序，落点跟着手指走，半行就进位。
